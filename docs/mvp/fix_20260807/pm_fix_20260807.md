- [ ] **Task 1: Add redirect to /onboarding after successful email code verification**

**Context:**  
 Registration flow: user enters email → password → receives a code by email → enters the code. Clerk's verification call succeeds (confirmed via Network tab: attempt\_verification and tokens requests return 200, and a valid session JWT is issued). However, **no redirect happens afterward** — the UI is left stuck showing a loading spinner indefinitely, and the user never reaches /onboarding.  
**Root cause (likely):**  
 The success handler for the OTP verification step does not include a navigation call. The code probably calls something like signUp.attemptEmailAddressVerification(...) (or the sign-in equivalent), but doesn't act on the result once it resolves successfully.  
**Requirements:**

1. After the verification call resolves successfully (status \=== "complete" from Clerk, or equivalent success check), explicitly navigate the user to /onboarding — e.g. router.push('/onboarding') in Next.js.  
2. Make sure the loading spinner is tied to the actual request state: it should stop as soon as the request resolves (success or failure), not spin indefinitely.  
3. If verification fails (wrong/expired code, server error), show a visible error message to the user and let them retry — don't leave them on an infinite spinner either way.  
4. Double-check: does Clerk's setActive({ session }) call (to activate the new session) also need to be called before/alongside the redirect? Worth confirming this step isn't missing too — it's a common cause of "verification succeeds but nothing happens" bugs with Clerk.  
5. Decide and implement what should happen for a user who logs in again after already completing onboarding — should they go straight to /onboarding again, or somewhere else (dashboard)? This affects where exactly the redirect logic should live (right after sign-up specifically, vs. a general post-login redirect).

**Priority:** High — this currently blocks every new user from reaching onboarding at all.

- [ ] **Task 2: Add a clear entry point to the onboarding chat**

**Context:**  
 When a user first lands on /onboarding, they see only a placeholder ("Say hello to start your onboarding interview") with an empty message input. There's no explanation of what this step is, what to expect, or an obvious way to begin — the user has to guess that typing something starts the flow.  
**Requirements:**

1. Add a short intro block above the chat, explaining what this step is and what happens next — e.g., "We'll ask you a few quick questions about your goals and English level to build your personalized learning plan. Takes about 2 minutes."  
2. Add a visible **"Start"** button (instead of relying on the user typing "hello" into an empty input) that kicks off the conversation with the coach's first message.  
3. Once the user clicks "Start," the coach sends its opening message automatically (the current first message — "Hello\! Welcome... What do you want to be able to do in English...") and the chat becomes active for the user to reply.

**Priority:** High — this is the very first thing every new user sees; if it's unclear, they may drop off before onboarding even begins.

- [ ] **Task 3: Onboarding AI-coach chat should ask one question at a time**

**Context:**  
 The onboarding chat currently works (goal → follow-up questions → presumably level/plan generation), but the coach sometimes bundles multiple questions into a single message (e.g., asking about industry, deadline, and self-assessed level all at once). This creates a wall of text that's harder for the user to respond to naturally.  
**Requirement:**  
 Update the AI coach's system prompt/instructions so that it always asks **only one question per message**, waits for the user's reply, then asks the next one — rather than listing several questions together. The conversation should feel like a natural back-and-forth, not a numbered questionnaire delivered in one message.  
**Example of current (undesired) behavior:**  
"1. What kind of job or industry are you interviewing for? 2\. Is there a deadline...? 3\. How would you describe your English today?"  
**Desired behavior:**  
Coach: "What kind of job or industry are you interviewing for?"  
 User: \[answers\]  
 Coach: "Got it. Is there a deadline for these interviews?"  
 User: \[answers\]  
 Coach: "And how would you describe your English today?" — etc.  
**Scope note:** This is a prompt/behavior change to the existing onboarding chat — no separate questionnaire form is needed. The chat itself should collect: learning goal, relevant context (industry/situation), timeline, current level, and available time per day, one step at a time, before generating the personalized plan.  
**Priority:** Medium — chat works, but this improves usability significantly.

- [ ] **Task 4: Fix chat message input — support line breaks and auto-growing height**

**Context:**  
 The message input in the chat (onboarding and elsewhere) has two related problems:

1. Any key combination (Enter, Shift+Enter, etc.) immediately sends the message — there's no way to insert a line break.  
2. The input box has a fixed height and doesn't grow with the text; longer messages require scrolling inside the small box instead of the box expanding to fit the content.

**Requirements:**

1. **Send vs. new line:** Pressing **Enter** sends the message. Pressing **Shift+Enter** inserts a line break instead of sending.  
2. **Auto-growing height:** As the user types (including across multiple lines), the input box should grow to fit the content — e.g., recalculate height on every input event based on scrollHeight (reset to auto, then set to scrollHeight).  
3. **Max height cap:** Set a max height (e.g., \~150–200px); beyond that, allow internal scrolling as a fallback so the send button and rest of the layout don't get pushed off-screen.  
4. Make sure the input element is a \<textarea\> (not a single-line \<input\>) so it can properly display and grow across multiple lines.

**Priority:** Medium — doesn't block the core flow, but affects usability for anyone writing longer answers to the coach.

- [ ] **Task 5: Redesign plan card interaction — add "Accept" / "Change" buttons, fix message ordering**

**Context:**  
 The "Proposed Plan" card currently only has an "Accept plan" button and appears to be rendered outside the normal chat message flow (likely as an overlay/sticky element rather than a real message in the array). This causes a bug where new chat messages sent after the plan is shown appear *above* the plan card instead of below it, and there's no clear way for the user to request changes to the plan.  
**Requirements:**

1. **Two-button plan card:**  
   * **"Accept"** — navigates the user to /dashboard (the existing page for starting lessons).  
   * **"Change"** — dismisses/removes the plan card and returns focus to the chat, so the user can continue the conversation with the coach to adjust the plan (e.g., "I want to focus more on X" or "reduce the daily time").  
2. **Fix message ordering root cause:** Make the plan card a proper item within the same messages array/list as regular chat messages (with a correct timestamp/sequence position), rather than a separately-positioned overlay element. This should resolve the ordering bug where new messages appear above it.  
3. **New plan version behavior:** If the user clicks "Change" and, after further conversation, the coach generates a revised plan, a **new** plan card (with the same Accept/Change buttons) should appear in the chat at that point in the conversation — the old plan card should not remain stacked below/above it as a separate, outdated card.

**Priority:** High — this is the core decision point of onboarding (accept vs. adjust the plan), so getting this interaction right matters a lot for usability.
