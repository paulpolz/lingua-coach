- [ ] **Feature: Persistent lesson checklist (top-right corner) synced with chat progress**

**Context:**  
When a lesson starts, the coach sends a lesson plan in the chat listing tasks and approximate time per task. This plan should also be displayed as a persistent checklist in the top-right corner of the screen, staying visible as the user scrolls through the chat. As the coach confirms in the conversation that a task is complete, the corresponding item in the checklist should be checked off / crossed out.

**Requirements:**

1. **Checklist UI:** A fixed/sticky panel in the top-right corner, listing all tasks for the current lesson with their reference time.  
2. **Data source & dual display:** When the coach's message includes the lesson's task list (structured JSON, same pattern as `course_roadmap`), it should:  
   * Render normally as a visible chat message, **same as today** — this stays unchanged.  
   * **Additionally** be parsed and mirrored into the pinned top-right checklist widget, so the same plan is visible in two places at once: in the chat history, and pinned for quick reference while the conversation continues below.  
3. **Completion trigger:** A task is marked complete **only** when the coach explicitly signals it via a structured block (see the `task_update` sub-task) — this updates the **pinned widget only** (checkmarks don't retroactively edit the original chat message).  
4. **Time display:** Reference label only, no active countdown.  
5. **Visual state:** Completed tasks are visually crossed out / greyed out in the pinned widget; the chat message itself stays as a historical record and doesn't need to update retroactively.

- [ ]  **Feature: Coach report files in the account menu**

**Context:**  
 The account dropdown (Clerk's `UserButton`, opened via the avatar icon — currently showing email, "Manage account", "Sign out") should get 4 additional menu items, each opening a dynamically AI-generated progress report as a formatted in-app page.

**Menu items (human-readable labels):**

1. **"Progress"** → renders the progress dashboard (per-category level, target, % progress, weaknesses, recommendations; top section covers the latest session's key findings; running update log)  
2. **"Error Log"** → renders the error log (running day-by-day log of mistakes \+ fixes; a "live pattern tracker" table of active/closed error patterns at the top; a word-family/sound-alike confusion list)  
3. **"Roadmap"** → renders the roadmap (milestones from diagnostic to B2 simulation, with success criteria per milestone, plus any scope adjustments)  
4. **"4-Week Plan"** → renders the current curriculum plan (day-by-day breakdown: grammar/vocabulary/listening/speaking/writing/interview-prep focus)

**Requirements:**

1. **Menu integration:** Use Clerk's `<UserButton.MenuItems>` with custom `<UserButton.Action>` items — Clerk supports adding custom items to its default menu, no need for a separate custom dropdown.  
2. **Rendering:** Each report opens as a nicely formatted markdown page inside the app (proper headers, tables, bold text, etc.) — never a raw text dump or file download.  
3. **Data source & generation (append/patch, not full rewrite):**  
   * Each report is stored as structured markdown per user (e.g., one DB row/document per report type: `progress`, `errors_log`, `roadmap`, `four_week_plan`).  
   * After each lesson, the coach outputs only the **new/changed section(s)** — a new dated entry, an updated table row, a new log line — rather than regenerating the whole file.  
   * Define two simple operation types for the coach's structured output: `append_entry` (add a new dated section, e.g. a new "Day N" log entry) and `patch_section` (edit a specific existing section in place, e.g. updating the progress table's percentages).  
   * This keeps generation cost proportional to what changed in a session, not to the full accumulated file size — important since `errors_log` grows indefinitely over time.  
4. **Access control:** Each report page is only viewable by the logged-in user who owns that data (standard per-user auth, consistent with the rest of the app).  
5. **Empty state:** Before the user's first lesson, each page should show a friendly placeholder (e.g., "Nothing here yet — this fills in after your first lesson") instead of a blank or broken page.
